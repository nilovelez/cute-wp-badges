# Plan

Milestones run one at a time, each started on Nilo's go-ahead and stopped for his review (see [AGENTS.md](../AGENTS.md)).

The project is a WordPress plugin, published on GitHub only (not in the WordPress.org directory). Badge drawing lives in a standalone JavaScript library that works both in the browser and in Node; the plugin uses it in an admin page and fetches the user's badges on the server, which avoids the CORS limits of profiles.wordpress.org (see [wporg-profile-api.md](wporg-profile-api.md)).

1. **Badge catalog.** `data/badges.json` with every badge: WordPress.org association slug, public name, team, team URL, profile CSS class, color, icon and whether it is a team badge. Research on how to get a user's badges from WordPress.org. *Done.*
2. **Badge library.** A JavaScript module, usable in the browser and in Node, that takes a badge id from the catalog, a format (SVG or PNG) and a size, and returns the image in the old style, checked against Nilo's reference image. It always builds an SVG and rasterizes it for PNG (canvas in the browser, resvg in Node). Every icon is an SVG file: the full Dashicons set, copied once from the official repository (https://github.com/WordPress/dashicons, archived and no longer adding icons), in `resources/icons/dashicons/`, and the custom team icons from the profile CSS in `resources/icons/custom/`. The Dashicons font copy goes away. `validate-badges` also checks that every icon in the catalog has its SVG file, and keeps a generated block in `.gitattributes` that `export-ignore`s every Dashicon SVG except the ones the catalog uses (`/resources/icons/dashicons/*.svg export-ignore`, then `-export-ignore` for each used icon), so the release zip only carries the icons it needs. Checked with a grid of Nilo's badges against his reference image. PNG output keeps a transparent background outside the badge. *Done.*
3. **Plugin skeleton and badge page.** The WordPress plugin with an admin page ("My WordPress.org Badges"): a badge selector, size and format fields, a preview and a download, using the library. A proof of concept of the WordPress integration: the plugin, the page, loading the library as a script module, drawing and downloading stay; the selector with every badge is temporary, until the user's own badges and the grid editor replace it. Script modules only load in wp-admin since WordPress 6.6, so that is the minimum version. *Done.*

4. **Tabs and the user's badges.** The page gets two tabs, which cover the two uses of the plugin: "My badges" (your own badges, from your profile) and "Any badge" (any badge in the catalog, for example a team badge for a contributor day). Both share the size, format, preview and download. "My badges" has a username field (the last one is remembered in user meta) and shows the badges of that profile as a picker. A REST route, `GET /cute-wp-badges/v1/badges/<username>`, reads `https://profiles.wordpress.org/<username>/groups/?num=100` on the server and caches it for 12 hours (`refresh` skips the cache). If the profile has a badge that is not in the catalog, the page shows a notice saying that the plugin needs updating (see "Updating the badge catalog" in the README). *Done.*
5. **Composed badges, selection, order and grid.** *Done.* First, every badge is composed once, on the developer's machine, into a finished, sanitized SVG file in `resources/badges/` (no ids, no metadata, nothing embedded, numbers kept as they are, solid colors only), which is what the plugin ships instead of the icons; the library only shows, nests or rasterizes these files: a grid as SVG nests the badge files as they are, and as PNG the whole grid is rasterized. Then the same interface in both tabs, with no separate single-badge and grid modes: you pick badges, and one badge gives that badge alone while several give a grid.
   - *Source.* "My badges": the username, as now. "Any badge": the catalog, with a search field and a "Team badges only" filter.
   - *Pick.* Thumbnails that toggle on click, plus "All" and "None". In "My badges" every badge starts picked; in "Any badge", none.
   - *Order.* A list of the picked badges: drag to reorder, ↑ ↓ buttons for keyboard users, ✕ to remove, and shortcuts to sort by profile order, by name or by team.
   - *Output.* Columns, badge size and gap (columns and gap hidden for a single badge), PNG or SVG, live preview and download. The background is always transparent.
   - *Library.* A new `renderGrid( ids, { columns, size, gap, format } )` next to `renderBadge()`, working in the browser and in Node.
   - *Saved state.* Per WordPress user and per tab, saved on every change through the REST API into user meta: picked badges, order, columns, size, gap and format. The page comes back as it was left. When the profile has a badge that the saved state does not, it shows up unpicked and highlighted ("New on your profile"); picking it adds it at the end of the order. A badge gone from the profile leaves the selection, with a notice.
6. **Media Library and settings file.** *Done, waiting for Nilo's review.* A "Save to Media Library" button next to download, with a notice linking to the new item. PNG images are uploaded through the core route `/wp/v2/media`, with a title and the badge names as alternative text. SVG images only when an administrator turns on a site option on the page, since WordPress does not accept SVG uploads: the browser sends the badges and the layout to a plugin route, which builds the SVG from the plugin's badge files, like the library does, so no SVG from the browser reaches the Media Library and other SVG uploads stay blocked. Next to it, "Export settings" and "Import settings": export saves the current design (picked badges in order, columns, size, gap and format; no username) to `cute-wp-badges-<yyyymmdd>.json`, and import loads such a file into the current tab; in "My badges", badges not on the loaded profile are left out, with a notice.
